## ENH-001 — Boxed review: single "co-located" box when value & subject share a marker
- **Trigger:** f1169e89 (#1, $63,029,917 total assets) and c31a2d63 (#1, "1035 – # of Empowerment clients served") — operator saw "no red box."
- **Cause:** when the grounding cites the **same marker for both value and subject** (`value_ref == subject_ref`, common for prose sentences and infographic stat-callouts where the number and its label sit together), the boxed review draws the red value box, then the blue subject box at the identical coordinates — blue paints over red, so the red is invisible.
- **Build:** when value & subject ground to the same marker (or near-identical bbox), draw **one box in a distinct color (purple)** labeled "value + subject — same passage," instead of two overlapping boxes. Only split into red/blue when they're genuinely different markers. (For different markers that happen to overlap, inset the second ring a few px so both show.)
- **Note:** this is a *rendering* fix; the underlying grounding in these cases is correct (value+subject co-located = good pairing).
- **Status:** queued

## ENH-002 — (observation, not yet an action) Docling bbox precision is weak on designed/infographic pages
- **Trigger:** c31a2d63 #1 — the box landed "in the area" but not on the glyphs: Docling's bbox for the green stat callout under-covered horizontally (stopped mid-line) and was offset vertically by ~1–2 lines.
- **Contrast:** on a clean financial table the same transform was pixel-perfect ($586,446 cell), and on prose (f1169e89) it landed correctly. So this is **Docling's spatial accuracy on visually-designed layouts**, not our coordinate transform.
- **Why it matters (operator, in priority order):**
  1. **PRODUCT / public-facing UX (primary).** If we ever surface provenance by *highlighting the metric on the actual report page* in a user-facing application, these coordinates drive that highlight. Loose/offset boxes = a poor end-user experience. This elevates the issue from internal QA to product quality — the bbox accuracy bar for a public feature is much higher than for our review tool.
  2. **Human reviewer friction (secondary).** For our own review, an offset box is harder to read but still "in the area," so it's tolerable internally.
  3. Spatial precision is weakest on exactly the infographic pages where number↔label mispairing risk is highest — the geometry we'd lean on to *catch* mispairings is least reliable where we need it. Relevant to the grouping-layer / infographic work.
- **Operator note:** there may be ways to make it work "as-is" (e.g., snap-to-region, highlight the whole callout rather than the glyph run), but this is recognized as an important and genuinely hard issue.
- **Status:** logged as a finding; no fix yet — gather more cases before deciding (re-OCR cell boxes? use char-spans? snap to a containing region? confidence-flag designed pages?).

## ENH-003 — Spatial pairing layer: detect + fix infographic mispairings from bbox geometry (PIPELINE)
- **Trigger:** 5b98b66f (Capstone Community Action) p2 — a "by the numbers" infographic with **4 published mispairings** (967 labeled "Head Start" but it's housing counseling; 353→"entrepreneurs" but it's Head Start; 369→"housing" but it's financial literacy; 2,971→"financial" but it's heating). The gate + all text/number analysis are **structurally blind** to these — 967 is on the page and "Head Start" is on the page, so every text check passes. The error exists only in the layout.
- **Method:** re-derive the number↔label pairing from the captured **bboxes** — each number → its spatially-nearest label. Where geometry **disagrees** with the model's reading-order pairing → mispairing flag. Where geometry is confident → use its pairing as the **fix** (re-pair, overriding the scrambled reading order).
- **Why it works without vision:** Docling's *reading order* is what scrambles the pairing (1-D flattening of a 2-D layout); the *bboxes preserve the 2-D arrangement*. Pairing needs only RELATIVE position, so the loose absolute precision (ENH-002) cancels out — a consistent offset doesn't change which label is nearest. The coordinates are the layout the flattening threw away. **This is the purpose of the prov/bbox capture.**
- **Two payoffs:** (a) metric-level triage — only scrutinize geometry-vs-model disagreements (vision-free, scales to 300k); (b) page/doc-level **risk flag** — high divergence = a designed page where the text is unreliable → route to spatial/vision handling, and *certify* agreement-pages as safe. This is the "know when the text is going to be wrong" detector.
- **Validated 2026-06-07:** on Capstone p2, geometry caught **4/4** real mispairings from coordinates alone and recovered the correct pairings. **1 false flag** (:7, 32=CKA graduates) from a naive nearest-centroid rule picking a side-column label.
- **NEXT before shipping to pipeline:** (1) tighten the pairing rule — "label directly below the number within its column," not raw centroid — until :7 clears; (2) **measure** recall/precision of the disagreement set across a sample of designed pages (does it concentrate the mispairings without drowning in noise?); then (3) wire as a pre-gate spatial-repair + risk-flag step.
- **Scope honesty:** catches SPATIAL/layout mispairings (infographics, multi-column) — the dangerous false-publish class. Does NOT catch non-spatial errors (a wrong/derived value on a cleanly-laid-out page).
- **DECISION 2026-06-07 — graduates from "flag" to "EXTRACT-and-PUBLISH" on designed pages.** Mispairings aren't bad metrics — they're GOOD data the flattening mis-attached. `2cf7c1e8:4`: model published "283 clients via partnerships"; the infographic shows **283 = Equine Assisted Learning** and partnerships = **155** — *every number on the page is real*. So quarantining wastes good data. Reframe: **on infographic pages, geometry IS the source of truth, not a detector** — re-pair each number to its physically-adjacent label and **publish that**. The model owns prose; geometry owns infographics (the model is structurally bad at them because flattening destroys layout). Crucial: **a geometry-paired metric is MORE provable than the model's** — "155 is adjacent to 'partnerships' on p1" is a bbox fact, cleaner provenance than a flattened-text guess — so publishing it is *consistent* with precision-first, not a shortcut. Architecture: detect designed page → geometry re-pairs → re-paired metric provable by bbox co-location → publish.
- **Safety before AUTO-publish:** (1) tighten the pairing rule ("label directly below, in-column" — clears the `:7` false flag); (2) grow the mispairing eval set to a real PRECISION number vs the <1% bar; (3) then auto-publish geometry-confident cases, route low-confidence to review. Bank it on the measured rate, not 5 examples.
- **Status:** queued for pipeline — scoped as the infographic EXTRACTOR (re-pair + publish), gated on measured precision.

## ENH-004 — Garble detector: doc-level parse-failure gate (UPSTREAM)
- **Trigger:** b9acbd60 (Orchards Children's Services) — the **entire document** parsed as `/gid00001/gid00035/...` (font glyph-ID leakage); the PDF itself is a clean, readable annual report (CEO letter, board lists). The model then **hallucinated** metrics from the gibberish ("served 1,000,000 individuals across 50 communities" — invented round numbers), and the gate correctly quarantined them.
- **This is the known ~0.3% garble class** (PUA glyph leakage / font-decode failure) from the parse-fidelity work — a WHOLE-DOCUMENT failure, not per-metric. Reviewing it metric-by-metric is wasted effort.
- **Detector (cheap, pre-extraction):** fraction of the doc's parsed text that is `/gidNNNNN` tokens or private-use-area glyphs; above a threshold → garble.
- **Action:** content is visually intact → **re-extract via pdftotext or OCR** (recoverable), else quarantine. Exclude from the extraction set the same way we exclude financial/plain-text.
- **Gap it exposes:** b9acbd60 reached the "clean" baseline because the report-filter checks `material_type` + plain-text, **not garble**. Garble is a separate upstream gate ([[project_corpus_inclusion_criteria]] — a third reject reason after financial/compilation and plain-text).
- **Status:** queued (corpus-inclusion / parse-quality gate). Cheap to scan the existing 166 baseline for other garbled docs.

## ENH-005 — Metric-validity / standalone-ness gate (SELECTION-quality)
- **Trigger:** "There was a 40% increase in client engagement" — the subject *"client engagement"* is a bare abstraction with **no object** (engaged in *what*?), so it can't stand alone even though value/direction/temporal (title-recoverable) are fine. **Same family** as 81265722:8 ("The Strategy is aligned with…" — true, verbatim, but not a self-contained metric).
- **The axis:** this is a **selection-quality / well-formedness** check — distinct from the grounding gate, which only verifies the value/subject are *real and located*, never whether the metric is *well-formed*. A metric can ground perfectly and still not be a metric.
- **v0 signal (cheap, deterministic pre-filter):** subject is a bare **relational abstraction** with no concrete object — `engagement`, `satisfaction`, `participation`, `involvement`, `retention`, `awareness`, `uptake`, `outcomes`, `impact` — flag. Real signal, free, but standalone-ness is ultimately semantic so the word-list misses subtler cases and can over-flag.
- **Robust check:** a **cheap LLM micro-check** per metric — "does this stand alone — is it clear *what* is being measured?" → drop/flag. Handles the semantic judgment a rule can't, and catches **both** vague-subject *and* framing-sentence non-metrics (the :8 type) in one pass. Doesn't touch the locked prompt.
- **Prompt option (weigh against drift):** add to selection "the subject must name *what* concretely; reject bare abstractions." Helps at the source but it's the locked virgin prompt (sha b51dc96a) and "be more specific" is a classic selection-drift risk — test before adopting.
- **Related flavors (same selection-quality axis), tag as found:**
  - **abstract / multiplier value** — model forces a *relational word* into the value slot: `040633b7:3` "the new building will **double** … served" → value=**2** (means 2×, not 2 of anything). Cheap signal: multiplier lexicon (double/triple/halve/quadruple) producing a small integer not present verbatim. **The verbatim-grounding gate already catches these** (the derived "2" can't ground → quarantine = `gate-correct`); we just tag to confirm consistency. Mode: `abstract-value`.
  - **projection / future** — "*will* double," "plans to serve," "projected" — a future intent, not an achieved outcome. Cheap signal: future-tense/modal lexicon.
- **Viewer:** `not-a-metric` and `abstract-value` added to the failure-mode list (cause = `selection`) to tag instances as they're found.
- **Status:** queued for pipeline (v0 = word-list pre-filter; v1 = LLM validity micro-check).

## ENH-006 — Two-stage quality-check harness (regex pre-filter → DeepSeek qualify) [BUILT]
- **The reusable engine** for semantically-fuzzy-but-rare quality gates. **Stage 1** = cheap regex over EVERY metric → tiny candidate set. **Stage 2** = DeepSeek (non-vision, our metric model) qualifies ONLY the candidates with a yes/no question. LLM cost scales with the regex-flagged **sliver (~1%)**, not the corpus → affordable at 300k.
- A "check" = `(stage1 regex, stage2 system+question)`. Swap those two; the harness handles the rest. Code: `loose_or_check.py`.
- **First plug-in — loose-OR-composite** (a single % counted as satisfied by ANY of an enumerated list of DISTINCT criteria — "X% feel A, B, *or* C" — which lowers the bar and inflates the number). Validated end-to-end on the 1,606 baseline: Stage 1 → **20 candidates (1.2%)**; Stage 2 DeepSeek → **6 confirmed (0.37%), 0 false positives**. DeepSeek made the calls regex couldn't: kept income-bands ("no/low/moderate income" = one variable), "one or two children" (a count), "$1,000 or less" (comparison), "meeting or exceeding" (phrase); and **caught the model-flipped case** (`d5cb6d0c:6` — statement says "and", source says "or") by reading the source. Output: `loose-or-quarantine.json`.
- **Key design fix:** Stage 1 requires the `%` in the metric's OWN statement (not just the source) — else a clean count metric whose source happens to contain a neighboring or-list gets falsely flagged (`81480a77:10`).
- **SUPERSEDED 2026-06-08 — the loose-OR check was MIS-AIMED.** It asked *"is the source a loose or-list?"* — but a source or-list is **faithful most of the time**: it punished the model for the report's own wording. On operator review, **5 of its 6 "confirmed" were actually faithful** (`d5cb6d0c:7`/`:8`, `68e0e142:3`, `93e81f02:9`, `2ec17b37:2` — the model kept the report's "or" verbatim) and have been **restored to published / gate-correct**. Only `d5cb6d0c:6` was a real defect — and that one is a *distortion* (the model rewrote the source's "or" as "and"), not source-looseness. The "0 false positives" claim above was wrong. **Replaced by plug-in #3 (paraphrase-drift)**, which asks the question that actually matters: did the model *change* the source's meaning? Lesson: flag what the MODEL did wrong, not what the source's wording looks like.
- **Plug-in #2 — measurable-value (BUILT 2026-06-08):** does the metric's number measure a real quantity, or is it a non-metric? Code `measurable_value_check.py`; output `measurable-value-quarantine.json`. Stage 1 = small integer values (≤20) are the suspects; Stage 2 = DeepSeek MEASURE/NOT. **Bar set at METRIC level, not KPI level** — KEEPS real counts (16 centers, 9 vans, 6 counties — those are metrics, just `input`/`output` tier) and only rejects true non-quantities: event-`1`s ("the legislature passed a bill"=1), multipliers ("doubled"=2), tallies of named items, identifiers. Calibrated 10/10. **RESULT / KPI: 92.5% genuine-metric rate** (121/1606 = 7.5% non-metrics). **Split: ~35% concentrated in narrative-genre docs** (curation — `12a4557a` Texas legislative **12/13**, `30259c4d` church-network **5/6**, `3c185ba6` 7/8 → [[project_corpus_inclusion_criteria]] / low-value-reports) **+ ~65% spread** (the prompt-attributable ~5%). **DECISION: handle the residue DOWNSTREAM (this check) + curation, NOT a prompt change** — selection is the strong crown jewel (92.5%), the residue is cheaply caught here, and the concrete value-rule prompt edit is deferred unless downstream proves inadequate at 300k. Also added `logic_tier` (input/output/outcome/impact) to the metric schema (`metric-schema.md`) — populated by a harness tagging step; KPI ≈ outcome.
- **Plug-in #3 — paraphrase-drift (BUILT 2026-06-08):** the replacement for loose-OR — does the model's STATEMENT change the SOURCE's meaning? Code `paraphrase_drift_check.py`; output `paraphrase-drift-quarantine.json`. Stage 1 = an "or" connective on either side (statement or source) + a substantive prose source to compare (94 candidates, 5.9%); Stage 2 = DeepSeek compares STATEMENT vs SOURCE → FAITHFUL/DISTORTED. **The defect class:** a source *disjunction* ("X% satisfy A, B, OR C" — counts if ANY) rewritten as a *conjunction* ("X% satisfy A AND B" — implies all) or members dropped/added, so the number now counts something different (`d5cb6d0c:6`: source "control, optimism, OR self-worth" → statement "control AND optimism").
  - **Precision lesson (important):** the v1 prompt over-fired at scale — **13/94 flagged, 12 false positives** — because real sources are full of *incidental* "or"s the faithful statement doesn't reproduce ("deficit or loss", "at or below", "minimum wage or more", "no support or resources"), which the model read as a "dropped clause." Fix: stage-2 prompt now judges only the **metric's own claim** and is told to ignore incidental "or"s elsewhere in the source. After tightening: **1 of 1,606 DISTORTED (0.06%) — exactly `d5cb6d0c:6`, 0 false positives** across the 13 verified.
  - **Takeaway:** paraphrase distortion is genuinely RARE; the model is faithful to source far more than loose-OR implied. Calibration on clean isolated cases (5/5) did NOT survive contact with real sources — always run the full set and verify the flags before trusting precision.
  - **Scope honesty:** currently catches the **or↔and / disjunction-collapse** class (the proven defect), scoped by the "or" pre-filter. Broader drift (dropped negations, "all" vs "most" quantifier swaps without an "or") is a future widening of stage 1.
- **Next plug-ins (same harness, swap the pair):** not-a-metric / standalone-ness (ENH-005), abstract-value, **logic-tier tagging** (classify input/output/outcome), **metric-type tagging** (the taxonomy categories).
- **Status:** BUILT + validated (measurable-value + paraphrase-drift live; loose-OR superseded). Reusable engine for the rest.

## ENH-007 — Grounding-repair: recover real metrics quarantined by a bad marker (PIPELINE)
- **Trigger:** `db75f054:7` ($2.3M fiber) — quarantined `value_not_at_marker`, but the value WAS at the cited marker; the *old* parser couldn't read "$2.3-million" (hyphen broke the scale-word). The hyphen patch to `candidate_numbers` recovers it. Investigating the class produced the measurement below. Code: `regate_value_quarantines.py` (faithful gate re-run, current parser) + `spot_verify_reground.py` (per-candidate source dump).
- **STALE-DATA WARNING:** the `claude` first-pass field in `review-data.json` for `value_not_at_marker` was computed with the **pre-hyphen-fix** parser — it is unreliable (it labeled `db75f054:7` "value appears nowhere / derived", the opposite of true). Do not trust it; `regate_value_quarantines.py` is the source of truth.
- **Re-gate of all 125 `value_not_at_marker` quarantines (current parser):** `2` recovered (now PUBLISH — `db75f054:7`, `8e1cf08b:0`; both `$X-million` hyphen casualties), `57` reground-strong (value+subject co-occur elsewhere), `4` reground-distinct, `34` reground-weak (small/common value, no subject = coincidence), `28` derived (value nowhere). **The raw "reground" count is coincidence-inflated** — 36 of the 57 strong have value <20 (event/award `1`s matching by chance).
- **Spot-verify of the 25 distinctive candidates (value ≥20, by eye vs source): 16 genuinely recoverable, 9 correctly held (~64%).** Recoverable patterns:
  - **Marker prefix-swap (11 of 125, the dominant + cleanest) — ROOT CAUSE CONFIRMED 2026-06-08:** the model writes the WRONG marker-type prefix while keeping the correct index — cites `c91` (cell) when it means `t91` (text). The cited ID usually **doesn't even exist** (9 of 125 cite a non-existent ID), but the **same-index opposite-prefix twin grounds the value** (`d58e3d5b:0` cited `c91` which doesn't exist; `t91` = "79 Individuals served 5,010 Night Hostings"). 11 ids: `c09c96c2:0`, `015893d4:3`, `d58e3d5b:0/:1/:2/:3/:4/:5/:9/:10` (8 — one night-hosting infographic), `128de607:0`; 9 also subject-confirmed at the twin. **NOT "empty cells" (my earlier wrong call): the cell isn't empty, the cited ID is out-of-range/wrong-type.** **Why:** `render_tagged` uses two independent counters (`t`, `c`) with overlapping integer ranges, so `⟨t91⟩` and `⟨c91⟩` look interchangeable to the model. Deterministic fix, near-zero FP.
  - **Genuine wrong-marker (~2-5):** cited an existing-but-wrong marker; value lives at a distant marker (`71709748:0` cited cell "247", value 643 at `t172`; `e31d17df:0` cited mission text, value $4,915,000 at cell `c42`). Needs page-search, not a twin swap.
  - **Rounded value grounded to the precise figure (~3):** "more than 1,300/2,000/100" grounds to the precise cell (1,324/2,200/110); the rounded value is verbatim in a prose marker (`81265722:0`, `fd032b14:1`, `fd032b14:3`).
  - **Label/value split, incl. off-by-one (~3-4):** cited the subject-label marker (no number); value in the adjacent number marker (`8bf02961:4`, `e136ede4:4`, `015893d4:0`).
- **The 9 NOT-recoverable = the gate working:** derived/summed (`370cd021:2` 600k−100k=500k; `7e9ebeba:2` 19+6=25), abstract-value (`ebaed191:8` "tens of thousands"=10000; `81265722:5`), **year-as-value** (`d58e3d5b:12`=2021, `370cd021:4`=1999), malformed/mis-attributed (`2ec17b37:0/:4`, `81265722:4`). Confirms the gate is NOT leaking real metrics at scale — most `value_not_at_marker` quarantines are correct.
- **Verified recoverable count ≈ 16-20 of 125** (~2% of the batch's metrics), heavily concentrated in the marker prefix-swap (11). Modest recall win, but the prefix-swap piece is high-value and dead clean.
- **Fix, in priority order:** (1) **PREVENT (root cause) — give markers one unambiguous ID namespace in `render_tagged`** (a single counter / kind-free IDs / non-overlapping ranges) so `c`/`t` can't be swapped. Changes the tagged INPUT, not the locked prompt (sha b51dc96a) — but needs a re-extraction to take effect, so do it before the 300k run. (2) **REPAIR (downstream, existing data) — twin-prefix re-ground:** when `value_ref` doesn't ground, try the same-index opposite-prefix marker; if it grounds value(+subject), re-ground there. Deterministic, recovers the 11 now without re-extraction. (3) guarded **page-search re-ground** for the ~2-5 genuine wrong-marker / rounding / label-split cases (require distinctive value ≥~1000 OR subject co-occurrence; never re-ground value <20). Precision-measure like [[ENH-003]] before auto-publishing.
- **Twin-prefix repair BUILT 2026-06-08** (`build_twin_repair.py` → `twin-repair-recovered.json`): re-grounds value_ref to its same-index opposite-prefix twin when the cited ref doesn't ground but the twin does, then re-runs the gate. **11 repaired → 10 publish** (9 solid: `d58e3d5b` ×8 + `128de607:0`; 1 marginal `015893d4:3` val=4 twin text ". 4" — eyeball). **1 correctly held** (`c09c96c2:0` val=2 — twin grounded the bare `2` by coincidence but the gate's subject check rejected it). The re-gate acts as its own guard — does NOT blind-publish twin matches. **review.db untouched (not auto-flipped); list is for operator marking.**
- **Render prevention DRAFTED 2026-06-08:** single ID namespace (`m##` from one counter, replacing the two `t`/`c` counters with overlapping ranges) in `render_tagged` so the prefix can't be swapped. Grep-confirmed downstream-safe: nothing infers cell-vs-text from the prefix letter — `gate.py:142` + `investigate_flags.py` use the `kind` field. NOT applied (changes tagged input → needs re-extraction); bake in before the 300k national run; keep twin-repair as the residual safety net.
- **Status:** root-caused + spot-verified + twin-repair built (10 recovered, pending operator marks) + render fix drafted (apply at re-extraction).
